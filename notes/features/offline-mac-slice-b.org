** R1: durable result and expiry contract
*** Common lock order (extends admit_launch, agents.ex:725-738)
MacWorker (only when the path involves the worker) → run → Operation
(share) → invocation → RemoteModelCall → charge (grant/allocation) → chain
head.

- No path that holds a run lock or any later lock ever requests the
  MacWorker lock.
- Disable and pause lock only the MacWorker row (FOR UPDATE).
- The settler never takes the MacWorker lock.
- The clock is read once, after every lock is held, as in launch_locked.

*** Claim (one transaction)
1. Lock the MacWorker row FOR UPDATE by token digest. It must be active
   with intake open; otherwise refuse.
2. Pick a candidate pending call without a lock, then take the chain from
   run to RemoteModelCall in order.
3. Re-check: call is pending, now < claim_deadline, worker has no claimed
   call. A unique partial index on RemoteModelCall(worker_id) WHERE state =
   'claimed' backs the worker check. If the check fails, roll back the
   candidate and return none.
4. Run the existing launch check (Admission.launch_check under the charge
   and head locks), then reserved → sent.
5. The call becomes claimed.
6. The commit happens before the response carries the launch input.

*** Complete (one transaction, authoritative deadline)
1. Lock MacWorker FOR SHARE, then run → … → RemoteModelCall.
2. Read the clock once.
   - If now ≥ result_deadline, the call becomes expired_unknown in this
     transaction. A `late` receipt is recorded, and nothing is applied. A
     late completion therefore never wins because the settler has not run
     yet.
   - If the worker is disabled, the result is refused and the call later
     expires unknown.
3. Otherwise, insert an immutable RemoteCallResult (call_id unique,
   transcript bytes, digest). The call moves claimed → completed, and a
   receipt is appended.
4. Settlement then runs in a separate transaction using the existing domain
   path (below).

*** Settlement and crash recovery
Settlement of a completed call:
- The existing claude_cli init attestation and finish_result run on the
  stored transcript, then the existing settle and the prototype release
  gate.
- It is idempotent because the invocation's sent → completed/failed
  transition happens once. A second attempt sees a terminal invocation and
  does nothing.
- The model is never rerun.

The settler cron (every minute, hosted) covers three cases:
- claimed past result_deadline → expired_unknown, invocation unknown,
  charged;
- pending past claim_deadline → expired_unclaimed, invocation failed from
  reserved, charged;
- completed with the invocation still `sent` (the waiting process died) →
  the settlement above, or `failed` with reason
  remote_result_unprocessable if validation cannot run. Never withheld
  silently.

Run termination: an orphaned run is not continued. After its invocations
are terminal, the existing StaleRunSweeper fails the abandoned run (job not
live). Continuation of the remaining steps is out of scope.

*** Immutability
- RemoteModelCall is a state machine:
  - pending → claimed;
  - pending → expired_unclaimed;
  - claimed → completed;
  - claimed → expired_unknown.
  Every terminal state is immutable. There is no `late` state, no
  settled_at and no conflict_count on the row.
- RemoteCallResult is immutable once inserted (digest and ref fixed).
- RemoteCallReceipt is an append-only event log: accepted, duplicate_same,
  conflict, late, refused_disabled. It holds the digest only, no content.
  Duplicates, conflicts and late arrivals are visible there.
- Settlement state is read from ModelInvocation, which already exists.

*** Mac launch-once
The Mac agent keeps a local launch journal, one 0600 file per call. It
holds ids only: call_id, claim_nonce, state requested → launching →
reported. Each state is fsynced before acting.
- Same-nonce claim retrieval is used only while the journal says
  `requested`.
- `launching` is written before the CLI starts. After a restart, a
  `launching` entry is never relaunched and never replayed; the call
  expires unknown.
- A lost or missing journal means the agent uses only new nonces and never
  replays an old one. Old claims expire unknown.
- This is not a child-kill requirement; the owner's waiver stands.

** R2: identity-scoped relocation and fork-safe rollback
Entities:
- Relocation: relocation_id; binding_id; relocation_seq, unique per
  binding and monotonic; from_identity and to_identity, each = (database,
  OID, system_identifier).
- RelocationEvent: append-only. Kinds: planned, writers_stopped, fenced,
  restored, activated, destination_disabled, aborted. Fields:
  relocation_id, kind, identity, recorded_at, recorded_by.

Main branch: planned → writers_stopped → fenced → restored → activated.

Abort branch, from any point before activated:
1. If restored exists, the owner runs `destination_disabled` ON the
   destination copy. The destination then refuses activation and boot for
   that relocation whenever this event exists, and the owner verifies that
   event's receipt.
2. Only then is `aborted` written on the source, which lifts the source
   fence.
3. If the destination's state is uncertain, there is no abort; the source
   stays fenced.

Predicates:
- Fence scope. A DB refuses writes when it holds a `fenced` event whose
  identity equals ITS OWN live identity and that has no later `aborted`
  for the same relocation. The copied `fenced` event names the source
  identity, so the hosted copy is unaffected.
- Current authority. The live identity equals the to_identity of the
  highest-seq relocation with an `activated` event. With no activation
  ever, it equals the binding's original identity.
- A return relocation is simply relocation_seq + 1. The unique index is
  (binding_id, relocation_seq), plus one `activated` per relocation_id.

Final fence serialization:
- Every audit-appending action (reserve, admit, assign, settlement and
  job-start writes) re-checks the fence AFTER Kernel.lock_head.
- The `fenced` event is appended under the head lock.
- A writer that locked first commits before the fence, so it is in the
  dump. Any later writer sees the fence and refuses.
- pg_dump starts after the fence commits.

History:
- The binding row is never edited.
- Grants, allocations, invocations, releases and their bases keep the
  original identity.
- New authority comes only from the relocation chain.

** R3: hosted owner authority and the prototype release path
*** HostedOwner (new)
- Fields: user_id; binding_id; relocation_id, the activation that enabled
  it; status (active, disabled); enrolled_at; disabled_at.
- Enrollment is owner-run on the host console. It is a single-use link,
  valid 15 min, created through a new owner-run action that is allowed
  only while the current-authority relocation is activated and no active
  HostedOwner exists.
- BootCheck delta: it admits the anchor, an optional bound auditor, and at
  most one active HostedOwner bound to the current-authority relocation.
- Disable is terminal and revokes all tokens.
- Actions:
  - read: the existing review_read under prototype rules;
  - assign: through the existing prototype OperatorAction resolver,
    extended to accept the HostedOwner subject;
  - MacWorker enroll, disable and intake.
- No retry (D-237 item 3 stands), no outreach and no settings changes.
- The kernel is never impersonated, and the auditor is never used to
  assign.

*** Authority mapping
- authority_core live_matches? (:841-845) compares the immutable binding
  row with the live identity. It changes to compare the CURRENT-AUTHORITY
  identity from the relocation chain with the live identity. The binding
  row stays the historical basis.
- Funding is unchanged: the same grant/allocation, consumption counted
  continuously, no reset.
- Release: the hosted runtime IS prototype runtime. `:released_unverified`
  stays available only through the prototype gate's Prelocked context
  (release_decision.ex:6-18).
- Historical releases are not rewritten. The flow never falls into
  ordinary witness-required processing.

*** Transcript attestation
- The Mac returns the full stream-json transcript: init event, messages
  and terminal result.
- The hosted side runs the existing attest(init, frozen profile) checks:
  model, CLI version, tools, MCP and slash commands (claude_cli.ex:1205-1215).
  It then runs finish_result.
- Binding is by call_id and request_digest echo. This is trust in the
  worker, not independent proof (R4).

*** RemoteRuntime (changed Runtime contract)
The hosted node has no local server, reaper, shim or local pin
(runtime.ex:12-35 does not apply).
- Health: MacWorker presence plus intake.
- Hold: intake paused.
- Profile identity: a frozen profile (resolved_model, cli_version,
  executable sha256) recorded at MacWorker enrollment from the Mac's
  reported pins and confirmed by the owner.
- Each heartbeat and claim carries the Mac's current pins. A mismatch
  refuses the claim.
- The Mac agent builds argv from its own pinned executable and code; the
  server sends data only, so there is no caller-selected executable or
  command.

** C2: nonce-to-call idempotency (replaces the r4 R1 claim steps)
New immutable entity, ClaimNonce:
- Fields: worker_id, claim_nonce, call_id (nullable), created_at.
- UNIQUE (worker_id, claim_nonce). Insert-only. call_id is set in the same
  transaction that inserts the row; it is never updated.

Claim transaction:
1. Authenticate the token. Lock MacWorker FOR UPDATE. Require active and
   intake open.
2. Look up ClaimNonce (worker_id, nonce).
   - If found with call_id X:
     - X is claimed and now < result_deadline: return X's launch input
       again;
     - otherwise: return X's terminal status, with no new work.
   - If found with a null call_id (an earlier claim with that nonce found
     no work): return "none". The nonce is spent.
   - A nonce NEVER acquires a different call.
3. Not found: select a pending candidate, take the run → … →
   RemoteModelCall locks, and re-check:
   - pending;
   - now < claim_deadline;
   - no claimed call for this worker (unique partial index kept).
4. Run launch_check, then reserved → sent and pending → claimed.
5. Insert ClaimNonce (worker_id, nonce, call_id, or null if there was no
   candidate).
6. Commit.

Client side: the transition requested → launching is an exclusive atomic
step across every local worker process, for example an O_EXCL create of a
per-call launching marker. The mechanism belongs in the implementation
plan. Only a process that wins that step launches.

** C3: completion order (replaces r4 R1 "Complete")
One transaction, under the lock order MacWorker (share) → run → Operation
→ invocation → RemoteModelCall:
1. Authenticate.
2. Resolve the immutable ClaimNonce (worker, nonce) → call_id. A mismatch
   is refused, with a receipt.
3. Compute the digest of the received bytes on the server. Any posted
   digest is ignored.
4. Inspect the state:
   - completed: the same digest returns the original receipt as a
     duplicate_same receipt. A different digest appends a `conflict`
     receipt. The result and state never change.
   - expired_unknown or expired_unclaimed: append a `late` receipt only.
   - claimed:
     - if now ≥ result_deadline: claimed → expired_unknown, and a `late`
       receipt;
     - if the worker is disabled: a refused_disabled receipt, and the
       state is unchanged; the settler expires the call later;
     - otherwise: insert RemoteCallResult (the first result is
       immutable), then claimed → completed and an `accepted` receipt.
5. A receipt never changes a terminal state. Deadline expiry and result
   insertion happen only from `claimed`. The settler uses the same locks.

Deadlines are proposed, not open: claim 120 s, result 600 s.
