* Deviations (each with its reason)
1. *Operator retry execution is split to S13b.* Brief item 5 is not built
   here, for these reasons:
   - Agent operations run with =max_attempts: 1=. =Operations.fail_operation/3=
     discards them in the same transaction, so =retry_operation/2=
     (=failed → running=) never applies to an agent Operation.
   - =Agents.retry_run/2= creates a queued run with no =operation_id=, and
     =AgentWorker= finds its run by Operation. Executing a retry therefore
     needs the =AgentRun :retry= action to accept the new Operation, and
     possibly =Operation= to admit an operator re-enqueue. Both are
     action-contract changes, which trigger the entity model and need the
     independent soft-stop review before implementation.
   - Delivery already retries automatically: =failed_retryable= is bounded
     at 3 attempts with backoff. S8 deliberately created no Operation rows
     for the delivery, reconciliation and follow-up queues (S8 choice 32).
     Wrapping them is a new persisted lifecycle use, so it falls under the
     same trigger.
   The Operations view therefore keeps S10b's behaviour (cancel,
   acknowledge and resolve; no retry button), and its moduledoc still says
   why.
2. *Live refresh uses Postgres NOTIFY, not domain broadcasts* (ADR-0012,
   proposed). NOTIFY is the only mechanism that is commit-exact on every
   write path. Run and Operations views are wired as well as the four that
   were asked for: they are one line each, and the run view is the "watch
   the agent" moment of the demo.
3. *The draft page does not live-swap revisions.* Swapping would undermine
   approval binding (the reviewer could approve content they had not read).
   A notice and a "Show the latest revision" button are shown instead, and a
   verdict on the displayed revision stays stale-checked by the domain.
4. *No live-server check.* A dev-mode server would use =sdr_agent_dev=
   (forbidden while the owner live-tests), and the test endpoint is
   =server: false= even under =phx.server=. The server path is covered by
   =bin/demo='s guard tests and the LiveView tests. The browser smoke is in
   the part-2 list.
5. *=bin/demo run= keeps the anchoring defaults* (=git+ots=). It prints the
   sink mode and whether the signing key is present (never its value). The
   README documents =SDR_ANCHOR_SINKS=file= for offline use. No default
   changed.

* Implementation Notes
- The tailwind =@source= glob (=.devenv/state/deps/*/…=) matched nothing,
  and =**/*= over-scanned (386 KB of CSS). Only an explicit directory works,
  so the toolchain tag is spelled out and pinned by a test. The fresh-worktree
  build is byte-identical to a build that has =./deps=.
- =bin/demo --test= suffixes =MIX_TEST_PARTITION= with =_demo=, so its reset
  never drops the database of the suite that runs it.
- =mix sdr.demo.status= starts the app with Oban queues and plugins off, so
  asking for the status never runs a job. Verifying the chain records a
  =chain_verify= AuditAccess, as every verification does.
- The notification payload is bounded by construction (≤ 512 bytes): ids,
  and short plain fields only; anything else is =null=, never truncated
  (review round 1, below).

* Review round 1 (Codex, PR #19 at =5e064b8=: CHANGES REQUESTED)
ADR-0012 design approved (now accepted, citing the ruling); choices 1–5
accepted. Fixed test-first:

1. *Reset could force-drop a live database.* It only checked the chosen
   =PORT=, so a server on another port (README suggests =PORT=4122=) lost its
   connections to =ecto.drop --force-drop=. Now =mix sdr.demo.clients= counts
   other =pg_stat_activity= backends of the target database (connecting to
   the =postgres= maintenance DB), =bin/demo reset= refuses unless it is 0
   (unreadable → refused) and drops *without* =--force-drop=, so Postgres
   refuses a client that connects in between. Tests: stubbed server on
   another port with 3 clients → refused, no drop; garbage count → refused;
   0 → plain =ecto.drop=; real =--test= client on the demo DB → refused and
   the seeded data survives.
2. *Unbounded NOTIFY payload could roll back a valid append.* =event_type=
   and =subject_resource= were unbounded (only =subject_id= was capped), so an
   oversized event exceeded the 8000-byte limit and failed its transaction
   (reproduced at RED: =Postgrex.Error= on the append). =LiveEvents.payload/1=
   now caps every field and admits only plain ASCII, dropping the rest to
   =null=. Tests: an oversized multibyte event commits on a real connection,
   and its notification arrives with =nil= fields; hostile values in every
   field stay within =max_payload_bytes/0= and contain no content.
3. Important: the moduledoc states the accepted failure coupling instead of
   "cannot block". =Demo.Status.ready?= now requires the fixture data set
   complete (=:seeded= vs =:incomplete=), a valid chain verification, and
   domain reads that succeeded (=:unavailable= otherwise). Tests: bootstrap
   only, a tampered chain, a missing verification. The draft page keeps
   refreshing lifecycle data (status, approvals, deliveries, history; an
   auditor's refresh is still audited) while the reviewed revision and its
   binding stay frozen. Test: an approval of the newer revision shows while
   the binding stays =#1=.
4. Inherited (owned by #17/#18): recipient binding, stale actor/session
   validation, tenant scoping and fail-closed reload state. =LiveRefresh=
   reuses =scope.user=, and NOTIFY is not an auth-invalidation mechanism.
   The owner-safe browser and golden-path checkpoint stays open before demo
   acceptance.

* Risks & Considerations
- *Quiet hours at the meetup.* The campaign fixture's quiet hours are 18:00
  to 08:00 America/Denver. An evening demo in Mountain time defers delivery
  until 08:00. The deferral is real behaviour and is recorded, but the
  "captured message" step will not complete live. Do not change the
  compliance defaults: present the deferral, or demo during the window.
- An audit append now also runs =pg_notify=. If it fails (notification queue
  full), the append fails. This is bounded and documented in ADR-0012.
- Live refresh is best effort: notifications sent while the relay is
  reconnecting are lost, and views update on navigation.

* S13 part 2 — progress on this branch (2026-10-07)
- *Golden-path e2e* =test/sdr_agent_web/golden_path_test.exs=: drives the
  console. The reviewer assigns lead 01 and the research job is drained.
  Qualification, evidence, the draft and the review queue appear. The
  approve form carries the displayed revision, hash and recipient email.
  The delivery is drained, the draft is =sent=, the captured message is
  read through the audited payload path, and the ledger holds every step in
  causal order (=sdr.lead.assigned= … =outreach.draft.sent=) with a valid
  chain. It is an acceptance test over existing behaviour, so it passed on
  its first run. A mutation check (an out-of-order expected event) fails it,
  0/1. *S9 slot:* =replies/2= gets the signed interested and unsubscribe
  replies (=WebhookFixtures=, =:integration= drain, suppression and
  follow-up cancellation) once this branch carries S9a (main =b26be34=);
  #19 stays based on s10b-ui until retargeted.
- *=bin/demo predeliver=* (=SdrAgent.Demo.Predeliver=, =mix
  sdr.demo.predeliver=). It runs lead 01 to a draft awaiting review and
  prints its =/drafts/…= path. It goes through domain APIs and the real
  research worker, drained inline, and waits (bounded) when a running dev
  server's Oban takes the job first. It is idempotent: a re-run only
  reports the stage, including the delivery after a human approval.
  *It never approves.* The first version had =--approve= (an approval as
  the Demo Reviewer fixture operator). The coordinator ruled that removed:
  a script approving as a fixture reviewer is not a human approval, which
  contradicts the ADR-0001 Tier 0 invariant even in dev. The owner approves
  in the console, which also rehearses the demo. Tests: an Approval is never
  created, whatever options are passed. RED was 19/21 against the
  =--approve= version (the script approved; =bin/demo= accepted the flag);
  GREEN is 21/21. Also tested: after a human approval and delivery, a
  re-run reports =:captured= and writes only its sign-in record, and
  =bin/demo predeliver --approve= is refused as an unknown argument.
