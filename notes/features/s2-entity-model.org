#+TITLE: Feature: S2 — MVP entity model (all domains, audit ledger)
#+DATE: 2026-10-06

* Summary
Define, before any resource is generated, every persisted MVP concept — its
attributes, relationships, lifecycle, authorization, audit emission and the
slice that creates it — so S3, S5–S9 and S11 build against one reviewed
contract. Docs only: no code, resources or migrations change in this slice.

* Entity Model

#+BEGIN_EXAMPLE

Reason: introduces every persisted domain, agent-provenance, audit-ledger and operations concept of the MVP, and changes the existing Accounts.User (roles, password, tenant).

** Conventions (apply to every row unless the row says otherwise)
Proposed as ADR-0009 (persistence conventions) and ADR-0010 (lifecycles).

- *IDs:* =id : uuid_v7= primary key (Ash =uuid_v7_primary_key=). Exceptions:
  existing =User=/=Token= keep their generated keys; =Payload= is keyed by
  =(tenant_id, sha256)=; =AuditChainHead= is keyed by =tenant_id=. Seed data uses
  explicit, fixture-declared UUIDs through =seed= create actions that accept
  =id= and are authorized only for the SEED actor in =:dev=/=:test=.
- *Tenant:* the =Tenant= resource lives in the lowest domain, =Audit= (the
  chain is partitioned by it), so every FK to it points downward. Every
  tenant-owned table has =tenant_id : uuid, required, FK tenants ON DELETE
  RESTRICT, immutable after create=, set from the actor's tenant by a shared
  change. Ash =multitenancy= is *not* enabled in the MVP (isolation is out of
  scope per ADR-0002); the column keeps the data shape and partitions the
  audit chain. *Deployment-level (no tenant_id):* Tenant, ProvenanceSnapshot,
  AuditSigningKey; in the MVP their AuditEvents append to the singleton
  tenant's chain. *Identities are written out in full in each row*: an
  identity that starts with =tenant_id= is tenant-scoped; one that starts with
  a parent FK (e.g. =draft_id=) is scoped by that parent; "global" is said
  explicitly. "WHERE" marks a partial unique index (used wherever a nullable
  column participates).
- *Trace correlation (ADR-0005):* every row of every new resource carries
  =trace_id : string (32 lowercase hex), required, non-zero= and =span_id :
  string (16 lowercase hex), required, non-zero= of the span in which it was
  created; every AuditEvent carries those of the span in which it was
  appended. The audit kernel starts a span (=sdr.audit.append=) when none is
  active, so bootstrap, failed sign-in, denial, scheduler and CLI events are
  traced too. This requires the OTel SDK to run (always-on sampling, exporter
  possibly =none=) in every environment, including tests — an S3/S4
  interface requirement; no class of record is untraced.
- *Time:* all timestamps are =utc_datetime_usec=, taken from the single
  injectable =SdrAgent.Clock= (never =DateTime.utc_now/0= in resources).
  Mutable resources carry =inserted_at=/=updated_at=; append-only resources
  carry =inserted_at= only.
- *APPEND-ONLY* = the resource exposes only create and read actions (no
  update, no destroy), and a Postgres trigger rejects =UPDATE=, =DELETE= and
  =TRUNCATE= on its table (defence against raw SQL). "Terminal-immutable" =
  updates allowed only while the row is in a non-terminal state and only to
  the listed columns; the trigger rejects any update of a terminal row.
- *No hard deletes anywhere in the MVP.* No resource below exposes a destroy
  action; lifecycle end is a state. (Tombstones are DEFERRED, see table.)
- *AE* = the action appends an =AuditEvent= *in the same database
  transaction* (shared Ash change from S3; if the audit append fails the
  domain write rolls back). Each AE payload carries the action name, changed
  attributes (after-image), non-sensitive arguments and =record_sha256= — the
  canonical hash of the full row after the write — so tampering with any
  non-ledger row is detectable by recomputation. "AE: all writes" means every
  create and update action on the resource.
- *State machines:* explicit per-transition update actions, guarded
  atomically (the from-state check is part of the SQL =UPDATE=), a DB check
  constraint on the state column, and a per-resource transition table that a
  test compares against the declared actions (ADR-0010; no
  =ash_state_machine= dependency). "→" lists allowed transitions; (T) marks
  terminal states.
- *Cross-domain references* follow the dependency direction below: a
  higher domain may hold an FK to a lower one; a lower domain stores a
  higher domain's id as a plain uuid (no FK) and validates existence in the
  orchestrating action.
- *Later FKs:* where a column's target table is created by a later slice,
  the earlier slice creates the column as a plain nullable uuid (or omits
  it, as stated in the row) and the later slice adds the FK constraint in its
  own migration. Rows say "FK added in Sn".
- *Append-only lineage (supersedes):* a correction is a new row with
  =supersedes_id = prior_row.id= (backward pointer; the prior row is never
  touched). Constraints: =supersedes_id= references a row of the same
  subject; partial unique (subject, ...) WHERE supersedes_id IS NULL (one
  root per subject); unique (supersedes_id) WHERE supersedes_id IS NOT NULL
  (each row superseded at most once — a concurrent second correction fails and
  must retry against the new head). Current row = the row with no successor:
  =NOT EXISTS (SELECT 1 FROM t AS n WHERE n.supersedes_id = row.id)=. Every
  new row for a subject that already has one must supersede the current row.
- *Actors* (Ash actor; every AuditEvent records the actor):
  ADM = User role admin; REV = User role reviewer; AUR = User role auditor
  (human, read-only; owner decision 2026-10-06); system actors are
  =%SdrAgent.Actor{type: ...}= structs, never Users: AGT agent_runtime (Jido
  actions), DLV delivery_worker, REC reconciler, WHK webhook_ingestor, SCH
  scheduler (Oban follow-up/cron), ANC anchorer, AUD auditor CLI (non-human, read-only CLI
  for verify/export; its only writes are AuditAccess/AuditExport records),
  KRN kernel (boot: provenance, definitions, chain head), SEED seeder
  (=:dev=/=:test= only; refused elsewhere). "reads" = ADM, REV, AUR and AUD
  may read; system actors read only what their actions need.
- *Auditor (AUR) contract:* read-only UI access to the Audit timeline, payload
  viewer, chain verification and exports, plus read access to the domain
  records a timeline links to (Users: display_name and role only;
  IntegrationCredential: provider and status only). AUR may never create,
  update or destroy anything — including approvals, suppressions, deliveries,
  drafts, leads, failures and users, and including its own password — with
  one exception: AuditExport create (plus the read-like generic actions
  Payload =read_content= and chain verify). The AuditAccess and AuditEvent
  rows its views produce are appended by the audit kernel under kernel
  context, not by an AUR-authorized action. Signing in and out remain
  possible: AshAuthentication token writes run under the existing
  AshAuthentication-interaction bypass (no actor), which is not an AUR
  mutation. An auditor's password is set or reset only by ADM
  (=set_password=). Enforcement: on every resource, placed after any
  AshAuthentication bypass, one guard policy whose last check authorizes
  everyone else, so it adds only the auditor denial and leaves the resource's
  other policies to decide (Ash: every applicable policy must pass, and a
  policy that reaches no decision forbids):
  =policy action_type([:create, :update, :destroy, :action]) do=
  =authorize_if action([:read_content, :verify_chain, :create_export])=
  =forbid_if actor_attribute_equals(:role, :auditor)=
  =authorize_if always()=
  =end=
  (the first line names only the actions that exist on that resource; on all
  other resources it is omitted). *Every* AUR view is audited: each auditor-reachable
  LiveView mount and each payload view, chain verify or export appends an
  AuditAccess (with its AuditEvent) naming the records shown; if that append
  fails the page or content is not served (fail closed). Test obligations:
  deny cases for AUR on every guarded action and every mutation of Approval,
  Suppression, DeliveryOperation, Draft, Lead, Failure and User (including
  its own password change through the AshAuthentication action); allow
  cases proving the guard does not block ADM/REV/system actors; each
  auditor-reachable route appends an AuditAccess.
- *Operator attention (in-app only; owner decision 2026-10-06):* the runtime
  sends no external messages. Every condition that needs a human opens a
  Failure row in the same transaction as the state change that causes it:
  AgentRun → failed, budget_exhausted or system-cancelled (class run_stopped
  or budget_exhausted); DeliveryOperation → unknown (reconciliation_required),
  failed_permanent or bounced (delivery_failed); Operation → failed or
  discarded; Lead → blocked; WebhookEvent → failed. The single attention
  query =Operations.list_attention/1= returns Failures with status open or
  acknowledged (severity, class, subject ref, reason, occurred_at,
  acknowledged_at), read by the Dashboard and Operations views (ADM, REV,
  AUR). Resolving the causing condition (e.g. reconciliation of an unknown
  delivery) resolves its Failure with a system note.
- *Denial audit contract:* mandatory for these *guarded actions*: Approval
  approve/reject/revoke, every DeliveryOperation transition, Payload
  =read_content=, AuditExport create, chain verify, User =create_user= and
  role/status changes, Suppression create, IntegrationCredential update,
  DeliveryOperation =cancel_retry=, Draft edit, and every mutation attempted by
  an AUR actor.
  Guarded actions are reachable only through their domain code interface,
  which is wrapped by the audit kernel's guard: on =Ash.Error.Forbidden= it
  queues an =authz.denied= event and appends it *after the outermost
  transaction has finished* (commit or rollback) — never from inside it, so it
  cannot deadlock on the chain-head lock or be rolled back with the denied
  write. The append goes straight to the kernel (no domain action, no policy
  evaluation), so logging a denial can never recurse into a guarded action.
  Recorded: actor_type (=anonymous= when the actor is nil or invalid),
  actor_id if present, resource, action, attempted subject id as an untrusted
  string capped at 64 bytes, trace/span ids; never arguments or content. A
  test enumerates the guarded actions and, for each, asserts both the
  Forbidden error and exactly one committed =authz.denied= event. Denials of
  other actions are not audited in the MVP.

** Not persisted as their own entities (by design)
- *OutreachProposal* (spec §9): the Zoi-validated model output lives in the
  ModelInvocation's parsed output; the draft_proposal Decision records the
  outcome; the agent DraftRevision plus its RevisionCitations is its persisted form.
- *Jido Signals*: each emitted signal appends an AuditEvent (category signal,
  event_type = the signal type, causation_id = the signal id). Jido's own
  persistence restores execution state only (spec §12) and is not a record.
- *Oban jobs*: Oban's table is the queue; Operation is the domain view.
- *Captured mailbox*: the capture adapter's receipt (DeliveryReceipt +
  Payload) is the stored message; there is no separate mailbox table.

** Cross-domain dependency direction
Lower layers never hold an FK to, or call, a higher one:

#+BEGIN_EXAMPLE
Audit  <-  Accounts  <-  Operations  <-  Agents  <-  Sales  <-  Research  <-  Outreach
(web, Oban workers, Jido actions/flows, mix tasks)  ->  public domain APIs only
#+END_EXAMPLE

- Every domain appends AuditEvents through the Audit kernel; Audit stores
  actor and subject ids as plain values and holds FKs only to its own
  resources. Tenant is an Audit resource, so =Accounts.User → Audit.Tenant=
  and every other =tenant_id= FK point downward.
- Agents sits below Sales: AgentRun.lead_id/campaign_id and Decision subjects
  are plain ids; Sales/Research/Outreach hold FKs to Agents rows.
- Sales never calls Outreach. Recipient-change invalidation is enforced at the
  Outreach send gate; enrollment checks of suppression are done by the
  orchestrating Jido action, which records a Decision.
- Cross-domain orchestration (flows, workers) lives above all domains and
  uses only code interfaces with an explicit actor.
