* Required clarification: stamp absence and threat boundary
There is NO independent append-only fact identifying C1-created jobs in
this design. A persisted job whose binding was removed cannot be
distinguished from an unmarked legacy job by re-reading that same row.
Do not claim otherwise or add a new marker implicitly during GREEN.

The command accepts no job/provider fields; no C1 or operator-facing
application API can omit, remove or rewrite its source-owned stamp.
Tests must prove the producer cannot commit an unstamped C1 job, including
rollback on failed stamping. Workers compare passed job data with the
actual persisted job. Omitting/changing the stamp only in a perform
argument must not evade the persisted stamp. Malformed persisted stamps
refuse. However, trusted backend or database-level edits that REMOVE the
stored stamp altogether are outside this guarantee: the resulting job is
indistinguishable from legacy and may retain legacy behavior. This is an
explicit residual, not coverage by the absent-binding test.

Choosing an independent durable C1 marker would require a separately
reviewed contract delta. It is not part of this slice.
