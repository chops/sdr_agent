#+TITLE: Feature: HubSpot CRM integration (design, entity delta, sliced plan)
#+DATE: 2026-10-07

* Summary
Design-only plan to integrate a free HubSpot developer test account as the
first real CRM adapter (spec §17), recorded in
=docs/adr/0013-hubspot-crm-integration.md= (proposed).

- Read-only import of companies and contacts into Accounts, Contacts and Leads.
- HubSpot as a research evidence source, treated as untrusted data.
- Outbox-driven writeback with dry-run mode and a kill switch.
- Polling sync with cursors.

No production code changes in this PR. Owner decision 2026-10-07: integrate
with HubSpot; test against a free developer test account; keep the app
personal and local (no hosting, no public webhook).

* Entity Model

#+BEGIN_EXAMPLE
Entity Model trigger: yes
Reason: adds a new top domain (SdrAgent.CRM) with four persisted resources, builds the deferred S2 IntegrationCredential row, extends Account/Contact/Lead/Suppression/ResearchArtifact/Decision/Operation (attributes, identities, actions, actor grants), and adds two system actors.
#+END_EXAMPLE

** Inputs
Binding:
- ADR-0001: synthetic data only; never weaken suppression, approval,
  idempotency or audit; no delivery path to a real recipient; no secret
  values.
- ADR-0002: reconstructable from Postgres.
- ADR-0004: no model tools.
- ADR-0005: span content rules.
- ADR-0008: no new dependency.
- ADR-0009: IDs, tenant column, append-only triggers, same-transaction AE,
  layering, synthetic guard.
- ADR-0010: explicit transition actions.
- The S2 conventions (=notes/features/s2-entity-model.org=). They apply to
  every row below unless the row says otherwise. AE, APPEND-ONLY, lineage,
  denial-audit contract and auditor guard are all unchanged.

** Layering delta (ADR-0009 item 7 amendment, proposed with ADR-0013)
#+BEGIN_EXAMPLE
Audit <- Accounts <- Operations <- Agents <- Sales <- Research <- Outreach <- CRM
#+END_EXAMPLE

- =SdrAgent.CRM= is the new top domain. It may hold FKs to, and call the
  public code interfaces of, every lower domain.
- Lower domains hold CRM ids only as plain uuids. The orchestrating CRM
  action validates them.
- No existing edge changes. H1b must add the amendment text to ADR-0009 when
  ADR-0013 is accepted.

** New system actors (=SdrAgent.Actor= types; code, not persisted)
- *CRS* =:crm_sync=: import, polling, opt-out suppression, writeback
  planning.
- *CRW* =:crm_writer=: claims and executes =CrmWriteOperation=s.
- *REC* (existing) resolves =unknown= writes.

None of the three may approve, edit drafts, manage users or lift anything.

** Not persisted (by design)
- *The service key.* It exists only in the gitignored sops file and the
  child-process environment.
- *HubSpot rate-limit headers.* Observed per request and folded into run
  counters. Never stored per request.
- *Properties of skipped (non-synthetic) remote records.* Only their remote
  id and skip reason are kept.

* Owner setup steps (H0; the owner does all of these, and agents never handle the key)
1. *Create the developer test account.* Sign in to your HubSpot account (a
   free standard account is enough). Go to *Development → Testing → Test
   Accounts → Create developer test account*, name it =sdr-agent-test=, and
   click *Create*. Agents never create accounts.
2. *Keep the portal synthetic.*
   - Delete HubSpot's seeded sample contacts, or leave them: they use a real
     company domain, so the importer will skip them.
   - Add synthetic data only, with company domains and emails under
     =.test=, =.example=, =.invalid= or =example.com/.net/.org=. H1b's
     =mix sdr.crm.seed_csv= writes a CSV of the demo fixtures that you can
     load with HubSpot's CSV importer.
   - Do *not* create HubSpot workflows that email contacts.
3. *Create the service key* in the test account: *Development → Keys →
   Service keys → Create service key*, named =sdr_agent-local=. Add only
   these scopes:
   - *H1:* =crm.objects.contacts.read=, =crm.objects.companies.read=.
   - *Later, at H2c only:* =crm.objects.contacts.write= and the
     single-contact subscription-status write scope (shown as
     =subscriptions-status-write= or =communication_preferences.*=).
     Add =subscriptions-status-read= only if H0 shows =hs_email_optout= is
     unreliable.
   - Add nothing else: no deals, owners, schemas, lists, =sales-email-read=,
     timeline, batch or sensitive scopes.

   If service keys are unavailable in the test account, use the fallback:
   =hs project create --distribution private --auth static --project-base app=
   with the same scopes. Install it into the test account and copy the token
   from the app's *Distribution* tab. Tell the agents which path you used,
   but never the token.
4. *Note the portal (Hub) ID* shown in the account menu. It is not secret.
5. *Store both values yourself.* After H1a merges (it adds the
   =.sops.yaml= rule and the =.gitignore= entry), run this from the project
   root:
   =sops secrets/hubspot.local.sops.yaml=
   In the editor, enter:
   #+BEGIN_EXAMPLE
   hubspot:
       service_key: <paste the key here>
       portal_id: "<hub id>"
   #+END_EXAMPLE
   Save and quit; sops encrypts the file to your age key.
   - Do not use =sops --set= with the key on the command line, because it
     lands in shell history.
   - Do not paste the key into any chat, issue or terminal.
   - The file is gitignored and never committed.
6. *Check without revealing the key:*
   =sops -d --extract '["hubspot"]["portal_id"]' secrets/hubspot.local.sops.yaml=
   prints only the portal id. Then run the read-only smoke test:
   =bin/with-secrets SDR_HUBSPOT_SERVICE_KEY SDR_HUBSPOT_PORTAL_ID -- mix test --only external test/external/hubspot_smoke_test.exs=
7. *Keep it alive and rotate it.* The test account expires after 90 days

* Risks & Considerations
- Service keys are a public beta with undocumented test-account support.
  Fallback C (static-auth project app) keeps the same secret path.
- DBV =2026-09= has 18-month support. The version is pinned in one module
  attribute, and bumping it is a reviewed change.
- Test-portal expiry deletes HubSpot-side data. Local rows survive, and a new
  portal id avoids identity collisions.
- Polling latency is up to 15 min. Deletions are seen only by the archived
  scan.
- In a rare =unknown= + not-found reconciliation, one duplicate note or task
  is possible. It is recorded and identifiable by marker.
- =STANDARD= (real) portals stay refused until the ADR-0002
  data-classification ADR.

* Questions (for the owner)
- *OQ-1* Credential: Service key (public beta) primary, with the static-auth
  project app as fallback. Do you accept a beta credential?
- *OQ-2* Secret location: a separate gitignored
  =secrets/hubspot.local.sops.yaml= (proposed) instead of adding to the
  tracked, committed =secrets/sdr_agent.sops.yaml=?
- *OQ-3* Lead creation from HubSpot. Proposed: an automatic rule (lifecycle
  stage subscriber/lead/MQL/SQL, lead status not UNQUALIFIED/CONNECTED/
  OPEN_DEAL, opt-out known false), never auto-assigned. Alternatives: only an
  explicit admin "create lead" per contact, or only members of one HubSpot
  list (needs =crm.lists.read=).
- *OQ-4* Writes to HubSpot status fields. Proposed: never touch
  =lifecyclestage=. Set =hs_lead_status= to =CONNECTED= on a matched reply
  and =UNQUALIFIED= on disqualify. Should a captured first touch also set
  =ATTEMPTED_TO_CONTACT=?
- *OQ-5* Local admin edits of HubSpot-linked records. Proposed: refuse edits
  to HubSpot-owned fields, since HubSpot wins. The alternative is to allow
  them and overwrite at the next sync.
- *OQ-6* HubSpot deletion. Proposed: archive locally plus a monotonic
  =crm_record_deleted= Suppression, reusing the tested stop side effects;
  restoring the record in HubSpot does not re-activate it. The alternative is
  archive-only.
- *OQ-7* When writeback goes live, should earlier =skipped_dry_run= items be
  replayed? Proposed: no, they are terminal. Only items still pending (mode
  =off=) are sent, and pending items older than 7 days are cancelled as
  stale.
- *OQ-8* Log captured sends as a Note stating "captured locally, not
  delivered" (proposed), not as an Email engagement with status =SENT=.
- *OQ-9* Keep real (=STANDARD=) HubSpot portals out of scope until the
  data-classification ADR exists? Proposed: yes.
- *OQ-10* A new portal's writeback ledger cursor starts at the current chain
  head (proposed), so old history is never written into a new portal.
